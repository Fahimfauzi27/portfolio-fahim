Trackza Core • Part 1

Handling Async Location Streams in Dart

During the initial development blueprint of Trackza, the primary technical friction was streaming frequency. Constant raw coordinate updates flooded the backend network layer, leading to high cellular battery drain on the driver's device.

The Solution Logic:

I applied a specialized distance filter layer inside the Dart ecosystem using the geolocator package setting. Instead of streaming coordinates continuously over arbitrary seconds, the tracking hardware only executes a network write if the campus transit vehicle moves structural coordinates by more than 10 meters.

Geolocator.getPositionStream( locationSettings: LocationSettings( accuracy: LocationAccuracy.high, distanceFilter: 10 ) ).listen((Position position) { updateBusLocationInFirestore(position); });

Result: Safely preserves host battery allocations while delivering hyper-accurate map locations.

Trackza Core • Part 2

Reactive Google Maps API Target Mapping

When the transport driver changes coordinates, the active student application interface must catch the map change immediately and update the localized vehicle position marker without disrupting the user's active UI view state.

The Google Maps Controller Logic:

Instead of re-instantiating the map state (which causes unpleasant screen flickering), I utilized the native GoogleMapController class to dynamically animate target coordinates smoothly over the viewport matrix.

mapController.animateCamera( CameraUpdate.newCameraPosition( CameraPosition( target: LatLng(liveLatitude, liveLongitude), zoom: 16.5 ) ) );

Markers are stored as plain reactive states in Dart, letting the Flutter framework rebuild map elements asynchronously without freezing the app thread.

Trackza Core • Part 3

Lightweight Live NoSQL Schemas

In a campus ecosystem with hundreds of active student devices checking routes, an un-optimized Firestore structure can instantly spike cloud database usage costs.

The Firestore Hierarchy Optimization:

Instead of logging an immutable list of tracking records for historical logs, I isolated active locations into a high-speed singular document schema. Student apps listen directly to this atomic document snapshot.

/unisza_bus_fleet (Collection) /route_alpha (Document) - bus_id: "UniSZA-B01" - is_active: true - current_coords: GeoPoint(5.397, 103.041) - last_updated: Timestamp

This keeps network fetch operations linear at O(1) lookup complexity, optimizing read efficiency across the entire student fleet.
